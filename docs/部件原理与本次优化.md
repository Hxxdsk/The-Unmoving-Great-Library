# 大图书馆工具箱：部件用途、原理与本次优化

基于本次工作区中的源码分析。此次只调整抖店批量上架及其测试、说明文件，其他业务组件代码未修改。

## 各部件的用途和原理

| 部件 | 用途 | 主要原理与代码位置 |
| --- | --- | --- |
| 启动器、首页 | 启动程序、检测依赖、打开独立组件、查看运行状态 | Windows 原生启动器位于 `launcher/`；`app.py`、`runtime_probe.py` 检查环境，`suite/hub.py` 通过子进程启动组件，`suite/registry.py`、`suite/extensions.py` 注册入口。某个组件退出不会主动关闭其他组件。 |
| 商品图片颜色配对 | 将商品图片与表格颜色、商品编码配对，导出命名图片 | `color_tool/data.py` 读取与整理数据，`pairing.py` 综合图片颜色识别、同名匹配和异名建议，限制图片的一对一分配；`previews.py`、`ui.py` 提供预览和手工核对。模型结果经校验后使用，缓存避免重复请求。 |
| 商品编码匹配 | 把聚水潭商品编码填入对应抖店商品规格 | 原脚本经 `suite/legacy.py` 加载，`matcher_adapter.py` 做界面和匹配增强。先手工确认款号与 PID 关联，再按颜色、尺码匹配；尺码括号备注不参与比较，实际尺码仍精确区分，有冲突的编码不强行填入。 |
| 送审资料生成器 | 将输入表转换为送审表，匹配品类、标准、面料及价格 | `generator_adapter.py`、`submission.py` 组织处理；`master_data.py` 读取 Excel 主数据，`materials.py` 按原文拆分面料/里料/填充物，校验没有改字或遗漏；`standards.py` 等提供规则和辅助判断，结果输出表格供核对。 |
| 送审拼接图 | 对同款同色的正反面图片排序并拼接 | `joiner_adapter.py` 在原脚本上增加队列、预览与 AI 排序；保留导入顺序，用户主动触发智能排序，确认正反面后用 Pillow 拼接输出。 |
| 抖店批量上架 | 读取多款素材，自动填写网站并保存草稿 | `listing/models.py` 扫描素材并记录状态；`ui.py` 提供标题、价格、库存与任务控制；`runner.py` 推进各款流程；`site.py` 与 `page.js` 识别页面、上传图片、填写规格、核验及保存；`vision.py` 分析颜色、尺码与体重。 |
| 通用 AI、流程记忆 | 统一管理模型调用、缓存和已验证操作 | `suite/shared_ai.py` 管理模型和请求分配；`suite/cache.py` 缓存结果；`listing/workflow.py` 保存已验证流程，`page_ai.py` 在控件变化时辅助定位。流程成功验证后才记忆，失败方案有失败记录。 |

`original_scripts/` 保存原始脚本，适配层在加载后扩展功能。`suite/tasks.py` 等把耗时工作放到后台，并通过队列或信号更新界面。

## 抖店的连接和执行链路

桌面界面 → 批量调度 → Playwright → 本机 WebSocket 桥接 → Edge 连接扩展 → 抖店标签页。

`listing/bridge.py` 监听带配对令牌的本机连接；`edge_extension/background.js` 将 CDP 命令转发给扩展创建的工作标签页。所有任务沿用当前 Edge 登录，扩展在同一专用普通窗口中新开后台标签页，普通浏览标签页不在任务可操作范围内。

每个货号依次经历：创建商品及上传主图 → 图文信息 → 水洗标与货号 → 颜色与尺码识别 → 颜色规格图 → 尺码体重 → 价格库存 → 核验 → 网站推荐标题 → 保存草稿并检查成功回执。

根目录的 `_抖店批量上架记录.json` 记录处理状态；结果不明确的保存标记为待核对，已有记录的任务不会自动重新创建。

## 本次修改

1. 原来 `EdgeSession.next_work_page()` 新建页后会关闭所有旧工作页。现在仅新建页，完成页停留在网站保存后的状态。连接或开始新批次也创建新的操作页，避免把以前的完成页导航回商品列表。
2. 增加“同时进行任务数”数字输入，默认 1；完成一款后补入下一款，运行数量不超过设置。保留的完成页不占执行名额。
3. 增加“全部并行”：当前勾选且符合执行条件的所有货号同时处理。默认读取后会勾选可执行货号；用户取消勾选、资料不全、已有记录的货号不自动执行。
4. 并行设置保存到原组件设置文件。运行时锁定这些设置，结束后恢复操作。
5. 新增 `listing/parallel.py`：所有 Playwright 对象由一个专用异步事件循环管理，各商品工作线程可同时等待自己的上传、页面响应和识别结果。只使用一个桥接连接，保持现有连接扩展协议。
6. 每个商品只看到自己的根标签页及其打开的子页，防止创建页或弹出页串到另一任务。任务不共享可变的 AI 模型回退状态。
7. 并行任务共用同一个任务记录对象，其写入锁保护记录文件；流程记忆的读取也受锁保护，避免其他任务更新时遍历失败。
8. 点击停止后不再补入新任务；驱动连接失效时停止补入并通知在途任务停止。已打开页不关闭，保存结果不明确时继续保留待核对状态。

## 使用

解压完整更新包并运行 `启动工具箱.exe`。打开抖店批量上架、读取目录、填写标题并勾选待处理货号。输入并发数量或勾选全部并行，再开始保存草稿。并发越大，浏览器和模型服务承受的同时工作量越大，实际速度也受网站上传及模型请求速度影响。

本次未改变草稿保存流程、商品字段规则和其他四个业务组件。

## 验证结果

本次合计 56 个不同测试用例通过，覆盖原有串行上架、断线恢复、流程记忆、扩展配对，以及新增页面保留、并行任务、弹出页隔离、并发上限、补位、停止和设置记忆。Python 编译检查及 `git diff --check` 通过。

连接协议测试使用本地 Chromium、原版扩展 JavaScript 和 Node 实现的 Chrome API 测试替身；模拟商品页面由本地夹具提供。并行协议测试使用不同货号前缀的图片，确认两款商品分别保存一次、详情图片未串款、断开任务后草稿页和普通用户页仍存在。原串行协议测试也已支持无显示器模式，验证重连后仍保留已保存编辑页。

这些检查没有操作真实抖店，也不代表已在实际 Windows Edge 安装扩展后完成真实店铺验收。

## 后续优化：自动尺码图、配色提速与详情排序

- 移除“颜色目录必须有文件名为尺码的图片”的扫描限制。AI 对全部颜色素材按内容分类，找出一个或多个真正的尺码表；即使图片名为手机默认日期名称也能作为尺码图。广告中的单个体重区间不等同于尺码表。
- 将正常的多色对照配色合并到尺码识别请求中，常规路径由四次模型请求变为两次。用原始单色图细节与对照图真实文字绑定，不再每次必做两轮重复对照。
- 返回服装主体框及对照格框，在本地比较主体颜色，避开图片共用的广告底色与品牌角标。文字不符、编号重复、区域冲突或主体颜色明显更接近其他对照格时不上传错误配图；黑色和深灰互换有专项检查。
- 尺码表首次只提交一份清晰图，只有体重未读完整时再放大复读。可信识别结果使用按内容校验的本地缓存；变化后的素材或页面颜色候选不会复用旧映射。
- Windows 使用 `StrCmpLogicalW` 的系统文件名排序，修复旧自然排序将数字开头图片排在 `!0` 前的问题。详情图顺序发送、逐张等待完成，消除网站按完成时刻追加图片导致的乱序。其他图片字段继续沿用原有上传方式。

专项测试使用任意文件名尺码图、三种裤子颜色/共同广告背景的合成素材和可控模型返回值，并模拟 `!0` 比其他图片上传更慢的页面。检查了正常路径两次请求、缓存命中不增加请求、内容和候选变化失效、近色互换拒绝，以及最终详情顺序。没有调用真实模型做速度/精度基准，也未操作真实店铺；实际识别耗时仍取决于配置的模型与网络。

此轮完整抖店回归：`pytest tests/test_listing*.py -q`，147 项通过；补充近色校验后的专项测试：`pytest tests/test_listing_source_optimization.py -q`，11 项通过。Python 编译及差异空白检查通过。
